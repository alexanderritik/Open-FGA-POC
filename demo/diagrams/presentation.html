Foundations

What is ReBAC, and why do we need it?

ReBAC (Relationship-Based Access Control): access is decided by the relationship between a user and a resource — not by a role name. e.g. "is this user a viewer of this zone, or of its parent project/client?"

Traditional RBAC
  • Permissions attach to a role (admin, editor, viewer)
  • A role is usually global, or per resource-type — not per single resource instance
  • Breaks down when one user needs different access to different individual resources
  • Breaks down when access should flow through a deep, changing hierarchy
ReBAC (OpenFGA)
  • A permission is a relationship tuple: (user, relation, object)
  • A grant is scoped to one specific resource instance (this zone, this client) — not a role name
  • Inheritance follows the real hierarchy: grant once at a client/project/zone and it flows down automatically
Choose ReBAC over plain RBAC when —
  • Sharing must be fine-grained and resource-specific ("this exact zone", not "all zones")
  • Permissions must flow through a deep, possibly-changing hierarchy (client → project → zone → zone → structure)
  • A fixed set of roles can't express it without exploding into hundreds of one-off roles

This PoC's proof: a single grant at client:govt-of-india#viewer automatically reaches every zone, nested zone, and structure beneath it — no per-resource role, and no code change when the hierarchy grows.

Foundations

OpenFGA = authorization source of truth

A clean split: OpenFGA knows the shape of "who can see what." Postgres knows everything else.

OpenFGA stores
  • Relationship tuples — (user, relation, object)
  • The authorization model (types + relations, e.g. model.fga)
OpenFGA does NOT store
  • Names or any business fields
  • PII
  • Anything from the schema page — that all lives in Postgres
Reference: OpenFGA's own architecture diagram at openfga.dev is a good companion visual to drop in alongside this split.

Operations & roadmap

Audit & logging with OpenFGA

Two separate logs answer two separate questions — and the same OpenFGA deployment scales to many applications.

Application audit_events (Postgres)

  • action — e.g. create, grant
  • result — success, denied
  • metadata — free-form context
  • created_at — when it happened
Answers: which user did what, and did it succeed?

OpenFGA's own changelog table

  • store_id — which OpenFGA store
  • user, relation, object — the tuple
  • operation — insert (grant) vs delete (revoke)
  • high-precision timestamp
Answers: when was this exact permission granted or revoked?

One OpenFGA deployment, many applications

  • Each application (or environment) gets its own store_id — fully isolated data
  • Each store can run its own authorization model — apps don't share a model
  • A mobile app plugs in the same way: same OpenFGA API, its own store_id / model_id
  • Onboarding a new application needs zero changes to OpenFGA itself

Operations & roadmap

Future foreseeable changes — how we tackle them

Two kinds of change we expect, and the playbook for each.

Category A

New / changed data on an existing table

client, project, structure, …

No authorization model change needed

It's just a migration in the application DB where that data actually belongs. OpenFGA tuples/model stay untouched.

Very small changes? Just migrate the extra column into the same table — no bigger change required.

Category B

A new hierarchy or client joins us

1 — Same hierarchy shape

Different naming, or a different number of nested zone levels.

→ Reuse the existing OpenFGA store + model: add the new client/zones as new objects & tuples.

2 — Genuinely new shape

A business structure this model doesn't fit at all.

→ Design a new OpenFGA authorization model, its own store for that hierarchy type.

Audit & logging safety net — OpenFGA's own changelog + our audit_events table record every grant/revoke and every zone/structure change across all outcomes above, so we can always trace what changed, when, and why.

Operations & roadmap

Suggestion required — how should services call OpenFGA?

Five integration shapes on the table, and which combination we'd recommend.

1

Separate service (centralized)

One shared OpenFGA deployment (its own store per app) that every consuming service reaches over the network. This is what's already running today.

2

Sidecar

An OpenFGA process co-located with each app instance (e.g. same pod). Adds a deployment per instance and fights the "one store per app" model.

3

Inter-service call

Any service reaches OpenFGA the same way it reaches another internal service. Not a distinct topology — it's option 1, described from the caller's side.

4

Middleware

The authorization check wired into each app's request pipeline (e.g. a FastAPI dependency), so routes never hand-roll checks. An app-side detail, not a topology.

5

Embedded client (shared library)

A thin SDK wrapper — like this PoC's app/authorization/service.py — that every service imports directly, instead of each team reinventing check/grant calls.
