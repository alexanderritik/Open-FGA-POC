Foundations

What is ReBAC, and why do we need it?

Access is decided by the relationship between a user and a resource — not by a role name.

Traditional RBAC
Role-based, not resource-based
Same access for every instance
Breaks on deep, changing hierarchies
ReBAC (OpenFGA)
Permission = tuple: (user, relation, object)
Scoped to one exact resource
Inherits automatically down the tree

Choose ReBAC when

1 Fine-grained, per-resource sharing 2 Access flows through a deep hierarchy 3 Fixed roles would explode into hundreds

Proof: one grant at client:govt-of-india#viewer reaches every zone & structure beneath it — no code change as the hierarchy grows.

Operations & roadmap

Every change traced, every app isolated

One event writes to two logs that answer two different questions — and one OpenFGA deployment keeps every application's data and model separate.

Example row — audit_events

action: grant · resource: zone:north · result: success · actor: user:admin

Example row — OpenFGA changelog

store_id: hierarchy-poc · tuple: (user:john, viewer, zone:north) · operation: write

Example

A mobile inspection app plugs into the same OpenFGA deployment with store_id: mobile-app and its own model — no shared model, no downtime for the existing hierarchy-poc store.

Operations & roadmap

Future foreseeable changes — how we tackle them

Three kinds of change we expect, and the playbook for each.

Scenario A

Adding metadata to an existing table

A new or changed field on client, project, or structure — not a new resource type.

No authorization model change needed

It's just a migration in the application DB where that data belongs. OpenFGA tuples/model stay untouched.

Example

Add a region_code column to projects — a one-column migration, zero OpenFGA changes.

Scenario B

A new hierarchy or client joins us

1 — Same hierarchy shape

Different naming, or a different number of nested zone levels.

→ Reuse the existing OpenFGA store + model: add the new client/zones as new objects & tuples.

Example

A new client, "Govt of Nepal," reusing the same Client → Project → Zone → Structure shape.

2 — Genuinely new shape

A business structure this model doesn't fit at all.

→ Design a new OpenFGA authorization model, its own store for that hierarchy type.

Example

A flat retail chain — Client → Store → Till — with no zones at all.

Scenario C

A new application joins us

A different application entirely — not a new client inside this one.

Zero changes to OpenFGA itself

The new app gets its own store_id and can define its own authorization model — fully isolated from ours.

Example

A mobile inspection app plugs into the same OpenFGA deployment with store_id: mobile-app — no shared model, no downtime for us.

Audit & logging safety net — OpenFGA's own changelog + our audit_events table record every grant/revoke and every zone/structure change across all three scenarios above, so we can always trace what changed, when, and why.

Operations & roadmap · SDK

The OpenFGA SDK — four calls, every language

Official client libraries just wrap the same HTTP/gRPC API. Whatever language a service is written in, it talks to OpenFGA through these four primitives.

Node.js Python Go Java .NET HTTP / gRPC
STAGE 1 Configure client
NEWOpenFgaClient()

Point it at a store (+ optional model id), the API URL, and credentials.

apiUrl · storeId · authorizationModelId
STAGE 2 Write
POST/write

Create or delete relationship tuples — this is how a grant or revoke happens.

writes: [ user, relation, object ]
STAGE 3 Check
POST/check

The core question: is this user related to this object, this way? A yes/no.

{ "allowed": true }
STAGE 4 List / Expand
POST/list-objects

The other direction: what can this user see, or who can see this object.

list-objects · list-users · expand

Same four calls in every SDK, only the syntax changes — this is the surface any new service integrates against to add authorization.
